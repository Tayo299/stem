# HSSC Backend

Java 21 / Spring Boot REST API backed by PostgreSQL. Flyway owns the schema; Hibernate is validation-only (`ddl-auto: validate`). There are no bundled exam questions, competition dates, school records, district names, or default admin credentials.

## Run

Provide `DATABASE_URL`, `DATABASE_USERNAME`, and `DATABASE_PASSWORD`, plus a base64-encoded `JWT_SECRET` containing at least 32 random bytes. For the first administrator, set `HSSC_ADMIN_EMAIL` and `HSSC_ADMIN_PASSWORD` (at least 16 characters); set both or neither. Set `UPLOAD_DIRECTORY` to a private, persistent path outside the public web root.

Set `CORS_ALLOWED_ORIGINS` to a comma-separated list of exact frontend origins. The local default allows `http://localhost:5173` and `http://127.0.0.1:5173`; production should set this to the deployed frontend origin(s), not `*`.

Set `HSSC_DISTRICT_ZONES` to the districts/zones supplied by the HSSC authority, in this format:

```text
CODE=District Name|Zone One,Zone Two;CODE2=Another District|Zone A
```

Startup inserts missing district codes and zones idempotently. The database is initially empty if this is omitted; the backend does not manufacture geographic data. Then run `mvn spring-boot:run` (or build with `mvn test` / `mvn package`). Flyway applies migrations automatically.

On Windows, after creating the `hssc` PostgreSQL login role and `hssc` database in pgAdmin, run `.\run-local.ps1` from the backend directory in a PowerShell terminal. It prompts for the database password and (optionally) initial admin credentials without storing them in the repository, generates a temporary JWT signing secret for that server process, and supplies the six configured districts and twenty zones. Keep that terminal open while testing; press Ctrl+C there to stop the API. The temporary JWT secret changes on each run, so users must sign in again after restarting.

## Main API

- `POST /api/auth/login`, `GET /api/me`, `GET /api/notifications`
- Public discovery/registration: `GET /api/districts`, `GET /api/schools` (active schools with zone/district metadata), `GET /api/sponsors`, `GET /api/policy`, `POST /api/registrations/schools`, and `POST /api/registrations/students`. Multipart variants `/api/registrations/{schools,students}/document` accept a JSON `registration` part and optional `document`.
- Frontend compatibility routes: `POST /api/schools/register` accepts the school JSON registration DTO or multipart fields (`email`, `password`, `confirmPassword`, `name`/`schoolName`, `address`, `zoneId`/`zone`) with optional `registrationNumber`/`schoolRegistrationNumber`, required principal fields (`principalName`, `principalEmail`, `principalPhone`), and optional `photo` or `document`. The school registration page submits multipart `POST /api/schools/register/with-students` with JSON parts named `registration` and `participants`, plus one repeated `studentPhotos` JPEG/PNG part per roster entry. Each school participant record (name, gender, age, parent/guardian name and phone number, home address, uniform photo) is persisted against the pending school and is not an enabled student login account. The authorized admin can review the roster at `GET /api/admin/schools/{id}/participants`; an active school account can view its own school details and roster at `GET /api/school/dashboard`. These uniform-photo roster entries are separate from `POST /api/students/register`, which remains available for individual student portal accounts and requires a parent/guardian name and phone number and home address along with `fullName` or legacy `firstName`/`lastName`, either `age` or ISO `dateOfBirth`, and `email`, `password`, `studentNumber`/`admissionNumber`, and `schoolId`; optional `gender` and student `phone` are supported. A photo part accepts JPEG/PNG only; the existing optional document field retains private PDF/JPEG/PNG support. Student accounts remain pending school review and the registration response never contains credentials.
- School/student accounts await review. A successful school registration remains `PENDING` and returns an explicit message that administrator approval is required before sign-in; a pending school login is denied with an approval-specific message. An administrator reviews `GET /api/admin/accounts/pending` and updates `POST /api/admin/accounts/{id}/status?status=ACTIVE|REJECTED`. The registration hierarchy uses `GET /api/admin/districts`, `GET /api/admin/districts/{districtId}/zones`, `GET /api/admin/zones/{zoneId}/schools`, `GET /api/admin/schools/{id}`, and `GET /api/admin/schools/{id}/students`; school detail records derive district and zone from each school's persisted zone relationship. Schools review their own students at `GET /api/school/students`, retrieve their own students' private upload metadata at `GET /api/school/students/{id}/documents`, download only those owned student uploads via `GET /api/documents/{documentId}`, and update status at `POST /api/school/students/{id}/status`.
- Authenticated active accounts can upload private PDF/JPEG/PNG documents at `POST /api/documents` (multipart `file`). Files have a 5 MB cap, file-signature checks, SHA-256 storage names, and are not exposed by a public file-serving route.
- Admin question banks: `/api/admin/question-banks`; import JSON batches at `POST /api/admin/question-banks/{id}/questions/import`. Requests contain the prompt, subject, positive points, options map, and correct option. Correct answers are only returned to administrators.
- Admin exam management: `POST /api/admin/exams`, `POST /api/admin/exams/{id}/publish`, and `POST /api/admin/exams/{id}/release-results`. Exam question counts must exactly match the per-subject quotas; the configured bank must have enough questions in each subject. Exam time allowance is fixed to 40 minutes on the server and also capped by the exam close time.
- Exam configuration remains explicitly per exam: `subjectQuotas` must sum to `questionCount`, and only imported bank questions are assigned. `anonymousAllowed` permits anonymous attempts against that same configured exam; it does not define a separate anonymous question pool or a default 180+20 allocation. No question-count split is inferred or seeded.
- A school account's online exam is one shared attempt for exactly two registered school participants. Both names are linked to that attempt, and the shared result is presented for both participants; school accounts with a different roster size cannot start it. Individual student-account attempts remain independent.
- Frontend exam paths: `GET /api/exams/active` returns only exams open now. `POST /api/exams/start` accepts optional `{"examId":"..."}` (omitting it works only when exactly one exam is open) and returns `attemptCode`, `startedAt`, `deadline`, and questions without answer keys. `PUT /api/exams/{examId}/answers/{questionId}` accepts `{"selectedOption":"A"}`; include `attemptCode` for anonymous attempts. `POST /api/exams/{examId}/submit` similarly accepts an optional `attemptCode` (or `?attemptCode=`). Named students can omit the code because their one attempt is resolved from their authenticated account.
- The response from `POST /api/exams/start` has the frontend active-exam shape: `{"id":"...","status":"IN_PROGRESS","questions":[{"id":"...","questionText":"...","subject":"...","options":{"A":"...","B":"...","C":"...","D":"..."}}],"remainingSeconds":2400,"attemptCode":"..."}`. The option map contains the labels configured for each question (normally A-D; no options or questions are fabricated). `GET /api/exams/{id}/time` returns `{"remainingSeconds":...}`. `POST /api/exams/{id}/events` accepts `{"reason":"PAGE_LEFT"}` or `{"reason":"BROWSER_REFRESH"}`; anonymous attempts must also provide their `attemptCode`. Event receipts are persisted in `exam_events`, and a first exit event immediately submits the attempt (or marks it timed out if the deadline has elapsed). Browser exit events are inherently best-effort; clients should also submit explicitly when possible.
- Frontend student views: `GET /api/student/dashboard`, `GET /api/results/me`, and `GET /api/leaderboard` (admins must pass `districtId`; students/schools are scoped to their own district; optional `examId` selects a specific released exam). `GET /api/admin/dashboard` exposes aggregate review/school/student/exam/attempt counts; existing `/api/admin/...` question-bank, exam, portal, account-review, audit, and document-review routes provide management resources.
- Authentication is Bearer JWT from `POST /api/auth/login` with `{"email":"...","password":"..."}`. Protected active-account routes require `Authorization: Bearer <accessToken>`. Anonymous exam start, answer and submit only work for exams explicitly configured to allow anonymous attempts; the returned `attemptCode` is required for subsequent anonymous writes and must be treated as a secret. `GET /api/exams/active`, student dashboards/results, and leaderboard routes require authentication.
- Students start one named attempt at `POST /api/exams/{id}/attempts`; anonymous starts are permitted only when explicitly enabled on that exam. Answer persistence/submit uses `POST /api/exams/attempts/answers` and `/submit`, passing the returned high-entropy `attemptCode`. For anonymous attempts that code is a bearer credential; keep it private.
- Result release, district portal controls and qualification: `PUT /api/admin/leaderboard-policy`, `PUT /api/admin/portal/{registration|exam_access|result_review}`, `PUT /api/admin/districts/{districtId}/portal/{key}`, and district leaderboard `GET /api/districts/{districtId}/exams/{examId}/leaderboard`. Tiebreak keys are explicit (`submission_time_asc|desc`, `student_number_asc|desc`) and are never silently selected. Equal entries crossing the configured qualifier cutoff are returned with `qualified: null` and `qualificationDecisionPending: true`.
- Content administration: administrators manage sponsors at `/api/admin/sponsors` and policies at `/api/admin/policies` (GET/POST plus item PUT/DELETE). Public GET endpoints expose active records only; the V16 migration deactivates Monika so it is no longer shown as an HSSC partner. Policies are stored as editable text in PostgreSQL.
- Administrative registration navigation: `/api/admin/districts`, `/api/admin/districts/{districtId}/zones`, `/api/admin/zones/{zoneId}/schools`, `/api/admin/schools`, and `/api/admin/schools/{id}` provide hierarchy and school detail. `DELETE /api/admin/schools/{id}` safely archives by disabling the school and its student accounts while retaining records needed by audit and competition history.
- Result release can be done globally with `POST /api/admin/exams/{id}/release-results` or independently for a district with `POST /api/admin/exams/{examId}/districts/{districtId}/release-results`. District release is persisted per exam/district; attempt scores remain hidden until that district (or the whole exam) is released and result review is enabled. Notifications include recipient-appropriate action URLs and retain per-account read tracking.

All errors use a JSON error envelope; request validation is centralized. Audit events are stored for registration, review, question/exam management, portal controls, result release, attempts, and document uploads. Health/readiness probes are available under `/actuator/health`.

## Operational notes

Use TLS at the ingress, rotate JWT secrets deliberately (rotation invalidates existing tokens), restrict database and upload-directory access, back up PostgreSQL and private uploads, and supply districts/zones/admin credentials through deployment secret/config management. Registration/exam/result-review portal switches are persisted in PostgreSQL; per-district exam-access and result-review settings override global settings.
